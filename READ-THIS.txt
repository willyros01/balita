THIS IS ONE CONSOLIDATED CHANGE, NOT ANOTHER SINGLE-QUESTION BUILD
The last test proved something concrete: the write succeeded and was
confirmed present immediately, yet was gone later, specifically after
the app had been backgrounded rather than freshly launched. That rules
out the write failing. What's left is something clearing it afterward.

Rather than add another trace question on top of the same storage,
this moves the one thing that actually matters - where the
notification's destination and the trace both live - to a different
storage system entirely. Cache Storage exists for network responses
and is something the browser reclaims when convenient. IndexedDB
exists specifically to hold a page's own data permanently, and is
treated far more carefully. Everything else already built stays
exactly as it was: the write-at-arrival design, the immediate
read-back check reported in the banner, the reload-before-focus
change to the tap, the start()-guard fix. Only the storage underneath
all of it has changed.

Also added in the same build: a request asking the browser to treat
this site's storage as important enough not to clear casually. Safari
does not always honor this, but it costs nothing to ask, and belongs
here rather than as a reason for a later build.

The helper code itself was tested directly against a real IndexedDB
implementation before this was packaged - round trips, overwrites,
ten concurrent writes firing close together the same way real events
do, and reading from an independently-opened connection the way the
worker and the page each will. All of it passed.
