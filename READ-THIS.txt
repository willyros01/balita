WHY THIS ONE IS DIFFERENT FROM EVERY PREVIOUS ATTEMPT
Every earlier build treated cold and background as though they should
behave the same way once a notification is tapped. They don't, and the
completely deterministic result across every test - cold always passes,
background always fails, on both devices, without exception - pointed
directly at what's structurally different between them.

A cold launch always forces a real, full page load. A background resume
never asked for one - it only asked the already-open window to come to
the front, on the assumption that alone would be enough to wake the
page's own checks. If that assumption doesn't hold on iOS, nothing was
ever going to wake up to look, no matter how solid the reading logic
underneath it was.

WHAT CHANGED
When an existing window is found, it is now asked to reload completely
before being brought forward - the same real page load a cold launch
already gets, rather than just being told to come to the front as it
was. If that succeeds, the background case should end up running
through exactly the same path that has already passed every time.

The trace records plainly whether that reload was accepted or refused,
so if this doesn't work either, we'll know that specifically rather
than guessing again.
