WHAT YOUR LAST TEST SHOWED
A different, more specific pattern than before: the very first tap
after a fresh install landed on the wrong story, but every tap after
it in that same session was correct - true in both the cold start and
background tests you ran.

MY HONEST READ ON THIS ONE
I can't prove this one the same way the last two were proven, since it
depends on exactly how the phone behaves in a narrow moment I can't
fully reproduce here. But there is a real, legitimate risk that fits
precisely: the durable storage this all depends on doesn't exist until
something first tries to use it, and right now that first use could
end up happening inside the notification handler itself, while
several are arriving in the background - a moment already known,
throughout this project, to be far more constrained than an ordinary
one. Everything after that first moment works, because by then the
storage already exists.

WHAT CHANGED
The storage is now created up front, during the app's own
installation - a moment the browser is documented to actually give
real time to, rather than leaving its first creation to happen under
pressure later. On top of that, every write and read now quietly
retries once, a fraction of a second later, if anything goes wrong the
first time - cheap insurance either way.

Re-ran every existing test against this version before packaging it -
the ordering, the clearing, the specific-tap priority - all still
behave exactly as before with this added.
